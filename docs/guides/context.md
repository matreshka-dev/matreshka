# Context

`Context<T>` — это главное серверное состояние страницы или отдельного UI-сценария в matreshka.

Через `Context` BFF:

- хранит данные, от которых зависит UI;
- синхронизирует эти данные с клиентом;
- получает изменения от клиента;
- отдает `ref()` для привязки к компонентам;
- валидирует входящие изменения, если задана схема.

Если коротко:

- `clientSettings` — это глобальная конфигурация приложения;
- `Context` — это состояние конкретного экрана, формы, списка или сценария.

## Самый маленький `Context`

```ts
context = new Context({
  data: async () => ({
    name: "Alice",
  }),
});
```

Здесь `data` — это функция, которая возвращает начальное значение контекста.

## `ref()`

Чтобы связать данные контекста с компонентами, используется `ref()`.

```ts
const nameRef = this.context.ref("name");
```

`ref()` не читает значение сразу, а создает ссылку на путь внутри контекста. Дальше эту ссылку можно передавать в компоненты.

Короткие примеры:

```ts
text(this.context.ref("name"));
```

```ts
textInput(this.context.ref("name"));
```

```ts
text(`Привет, ${this.context.ref("name").toString()}`);
```

Подробные примеры использования `ref()` с `forEach` и другими компонентами — в [components-basics.md](components-basics.md) и [components-list.md](../reference/components-list.md).

## Изменение значения на BFF

Если нужно обновить данные из серверной логики:

```ts
this.context.setValue("name", "Bob");
```

Если нужно не только менять контекст, но и реагировать на его изменения, можно подписаться на `data$`:

```ts
this.context.data$?.subscribe((data) => {
  console.log("Новое состояние контекста:", data);
});
```

Но здесь важно помнить про жизненный цикл подписки. Если обработчик больше не нужен, от него нужно отписываться, иначе можно получить лишние реакции, утечки памяти или обработку уже неактуального UI-сценария.

Для `entry`-компонентов удобный паттерн — привязывать подписку к `destroy$`:

```ts
import { takeUntil } from "rxjs";

this.context.data$?.pipe(takeUntil(this.destroy$)).subscribe((data) => {
  console.log("Контекст изменился:", data);
});
```

Такой подход особенно полезен в `Page`, `Dialog` и других `entry`-компонентах: когда `entry.destroy$` срабатывает, подписка автоматически завершается.

Это один из самых частых сценариев:

- реакция на клик;
- submit формы;
- ответ от сервиса;
- загрузка следующих данных;
- серверная бизнес-логика.

## Способы инициализации `Context`

У `Context` есть три основных режима инициализации.

### 1. `preload`

```ts
context = new Context({
  preload: true,
  data: async () => ({
    draft: "",
  }),
});
```

`preload: true` заставляет BFF подготовить контекст заранее при авторизации клиента.

Это полезно, когда:

- данные точно нужны сразу;
- страница почти мгновенно опирается на этот контекст;
- вы не хотите ждать первого клиентского запроса к контексту.

### 2. Lazy-инициализация

```ts
context = new Context({
  data: async () => ({
    draft: "",
  }),
});
```

Если `preload` не указан, контекст инициализируется lazy: данные загружаются при первом клиентском запросе этого контекста (когда он потребуется для отображения компонента).

Это хороший вариант по умолчанию, когда:

- контекст может вообще не понадобиться;
- загрузка дорогая и не должна происходить заранее;
- вы хотите откладывать инициализацию до реального использования.

### 3. Ручной вызов `init()`

```ts
class ProfilePage extends Page {
  context = new Context({
    data: async () => ({
      name: "Alice",
    }),
  });

  override async boot() {
    await super.boot();
    await this.context.init();
  }

  protected title() {
    return "Профиль";
  }

  protected content() {
    const name = this.context.value("name");
    return [text(`Пользователь: ${name}`)];
  }
}
```

`boot()` — метод entry-компонента, здесь `ProfilePage`. BFF вызывает его до
сериализации страницы и до вызова `content()`. Поэтому ручной `init()` нужен,
когда загруженные данные контекста должны участвовать уже в построении разметки:
например, `content()` или `overlays()` вызывает `context.value()` либо строит
ветки и списки на основе полученных значений.

Если разметка использует только `context.ref()` и клиентские `conditions`, обычно
не нужно загружать значение вручную перед сериализацией.

### Практическое правило

- `preload` — когда данные точно нужны сразу;
- lazy — когда данные могут понадобиться позже;
- ручной `init()` в `boot()` — когда данные нужны серверу для построения
  `content()` или `overlays()` до отправки разметки клиенту.

## Валидация через `zod`

Если клиент может менять данные, полезно сразу задавать схему:

```ts
import { z } from "zod/v4";

context = new Context({
  schema: z.strictObject({
    email: z.string().email(),
  }),
  data: async () => ({
    email: "user@example.com",
  }),
});
```

Теперь изменения `email`, пришедшие с клиента, будут валидироваться.

При этом первичный смысл такой валидации — не только проверить бизнес-правила вроде "это действительно email", но и убедиться, что типы значений, приходящих от пользователя, совпадают с типами, которые описаны в контексте. Это защищает BFF от ситуаций, когда вместо ожидаемой строки, числа, массива или объекта приходит значение другого типа и дальше вызывает непредвиденные ошибки в логике приложения.

Если значение не пройдет валидацию, обновление не будет применено, а ошибка уйдет в стандартный поток ошибок клиента. Практически это означает, что контекст не примет невалидное значение.

Например, если схема требует `z.string().email()`, а пользователь пока ввел только `test@`, это еще не полноценный email. Такое значение не пройдет валидацию и не попадет в `Context`.

Из этого следует важный практический вывод: слишком строгую валидацию не всегда удобно вешать прямо на "живое" поле ввода, которое обновляется на каждый символ. Для таких сценариев часто лучше:

- либо хранить в контексте более мягкий `draft` и валидировать его позже, например при submit;
- либо использовать схему, которая допускает промежуточные состояния ввода;
- либо разделять "черновое значение" и "валидированное значение".

Это особенно важно для:

- форм;
- фильтров;
- пользовательского ввода;
- данных, которые возвращаются с клиента обратно в BFF.

## `strictRef()` и ссылки на другой контекст

В общем случае `ref()` может использоваться не только как ссылка на фиксированный путь, но и как основа для более сложного пути. Например, путь можно продолжать через другой `ref`. Однако такой способ нормально типизируется только в рамках одного и того же контекста, потому что TypeScript может строго вывести типы только пока речь идет об одном дереве данных.
Простой пример внутри одного контекста:

```ts
context = new Context({
  data: async () => ({
    userId: 1,
    users: [{ name: "Alice" }, { name: "Bob" }],
  }),
});

text(`Пользователь: ${this.context.ref("users").ref("userId").ref("name")}`);
```

Идея здесь такая: значение `userId` участвует в построении пути к `users[userId].name`, но все это происходит внутри одного и того же контекста.

Когда ссылка должна строиться через значение другого контекста, обычного `ref()` уже недостаточно. Здесь появляется `strictRef()`: он более строг к описанию типов контекстов, но зато позволяет безопасно строить кросс-контекстные ссылки.

То есть:

- обычный `ref()` хорошо подходит для путей внутри одного контекста;
- `strictRef()` нужен, когда путь в одном контексте зависит от значения, лежащего в другом контексте.

```ts
const cardsContext = new Context({
  data: async () => ({
    cards: [{ title: "A" }, { title: "B" }],
  }),
});

const indexContext = new Context({
  data: async () => ({ key: "0.title" }),
});

const dynamicCardTitleRef = cardsContext
  .ref("cards")
  .strictRef(indexContext.ref("key"));
```

Это advanced-сценарий, но он полезен, когда путь к данным должен определяться динамически.

## In-place mutation

Это скорее `bad practice`, а не основной рекомендуемый способ работы с контекстом.

Если вы мутировали объект из `data$!.getValue()` вручную, нужно явно опубликовать обновление:

```ts
const data = this.context.data$!.getValue();
data.items.push({ id: "3", title: "Новый элемент" });
this.context.emitAfterInPlaceMutation();
```

Иначе подписчики и клиент не увидят изменения.

В обычной разработке предпочтительнее:

- либо обновлять значения через `setValue()`;
- либо собирать новое значение и заменять его явно;
- а к in-place mutation прибегать только в редких случаях, когда это действительно нужно.

Это важный момент, потому что:

- `setValue()` сам публикует изменение;
- ручная мутация объекта без `next()` не публикует ничего;
- `emitAfterInPlaceMutation()` нужен именно для таких случаев.

## Что приходит с клиента

Если компонент связан с `ContextRef`, клиент может присылать изменения в BFF.

На практике это означает:

- input-компонент меняет значение;
- клиент отправляет update;
- `Context` применяет изменение;
- при наличии `schema` выполняется валидация;
- подписчики и UI получают новое состояние.

Подробный протокол этих сообщений описан в [`../architecture/protocol.md`](../architecture/protocol.md).
