# Context

`Context<T>` — это главное серверное состояние страницы или отдельного UI-сценария в matreshka.

Через `Context` BFF:

- хранит данные, от которых зависит UI;
- синхронизирует эти данные с клиентом;
- получает изменения от клиента;
- отдает `ref()` для привязки к компонентам;
- валидирует входящие изменения: клиент меняет только ключи, описанные в `schema`.

Если коротко:

- `clientSettings` — это глобальная конфигурация приложения;
- `Context` — это состояние конкретного экрана, формы, списка или сценария.

## Самый маленький `Context`

Ниже в примерах подразумевается импорт `createContext` из `@matreshka/bff/core`.

```ts
import { createContext } from "@matreshka/bff/core";

context = createContext({
  data: async () => ({
    name: "Alice",
  }),
});
```

Здесь `data` — это функция, которая возвращает начальное значение контекста.

## `ref()`

Чтобы связать данные контекста с компонентами, используется `ref()`.

```ts
const nameRef = this.context.ref("name");
```

`ref()` не читает значение сразу, а создает ссылку на путь внутри контекста. Дальше эту ссылку можно передавать в компоненты.

Короткие примеры:

```ts
text(this.context.ref("name"));
```

```ts
textInput(this.context.ref("name"));
```

```ts
text(`Привет, ${this.context.ref("name").toString()}`);
```

Подробные примеры использования `ref()` с `forEach` и другими компонентами — в [components-basics.md](components-basics.md) и [components-list.md](../reference/components-list.md).

### `ContextRef`: чтение и запись по ref

Объект из `ref()` — это `ContextRef`. Его удобно передавать в компоненты **и** использовать в коде BFF, когда путь уже известен:

```ts
const nameRef = this.context.ref("name");
const current = nameRef.get(); // прочитать
nameRef.set("Bob"); // записать
```

`ref.set()` внутри вызывает `context.set({ … })` — клиент получит те же обновления, что и при записи через контекст.

На BFF `context.set(...)`, `context.replace(...)` и `ref.set(...)` возвращают **hot `Observable<ContextUpdateDelivery>`**:

- update стартует **сразу при вызове метода**;
- на каждый transport-level receipt у очередного клиента — `next({ delivered })`, где `delivered` — **накопительный** список `Client`;
- `complete` — когда receipt получены от **всех** ожидаемых адресатов diff;
- если diff пустой или адресатов нет — один `next({ delivered: [] })` и `complete`.

Тип `ContextUpdateDelivery` экспортируется из `@matreshka/bff/core`. Подробности — [../architecture/context-update-delivery.md](../architecture/context-update-delivery.md). Для финала доставки используйте `complete` или `lastValueFrom`, а не `firstValueFrom` (он даёт только первый прогресс).

Если ref уже пришёл в хелпер (`ContextValueRef`), не нужно снова искать путь:

```ts
import type { ContextValueRef } from "@matreshka/bff/core";

function finishSubmit(loadingRef: ContextValueRef<boolean | undefined>) {
  loadingRef.set(false);
}
```

После `destroy()` вызовы `get` / `set` / `replace` и `ref.set()` **бросают ошибку**; после async проверяйте `isDestroyed()`.

Для мгновенного UI **из actions на клиенте** используйте `context.local.set(patch)` или `ref.local.set(value)` — см. [events-and-actions.md](events-and-actions.md). На BFF в обработчиках и `ServerAction` — `ref.set()` или `context.set()`.

## API контекста на BFF

Кратко, чем пользоваться в коде страницы и сервисов:

| Задача                             | Метод                                                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| Прочитать поле по пути             | `context.get("path")` или `ref.get()`                                                             |
| Обновить одно или несколько полей  | `context.set({ … })` — ключи с dotted-путями, hot `Observable<ContextUpdateDelivery>`             |
| Заменить всё состояние целиком     | `context.replace(data)` — после load или готового снимка, hot `Observable<ContextUpdateDelivery>` |
| Скопировать всё `T` на время async | `context.snapshot()`                                                                              |
| Подписаться на изменения           | `context.watch()`                                                                                 |

Примеры:

```ts
const tab = this.context.get("activeTab");
this.context.set({ sending: false, message: "" });

const loaded = await this.api.loadProfile();
this.context.replace({ ...loaded, draft: this.context.get("draft") });
```

`get` для объектов и массивов отдаёт **копию** — правки «на месте» без `set` / `replace` контекст не меняют.

Если вам не нужно ждать доставку diff, можно по-прежнему вызывать `context.set(...)` / `replace(...)` в fire-and-forget стиле: update уже стартовал. Подписка нужна, когда важно отслеживать `delivered` по клиентам или дождаться `complete`.

## Подписка на изменения

Если нужно не только менять контекст, но и реагировать на обновления, подпишитесь на `watch()`:

```ts
this.context.watch().subscribe((data) => {
  console.log("Новое состояние контекста:", data);
});
```

Но здесь важно помнить про жизненный цикл подписки. Если обработчик больше не нужен, от него нужно отписываться, иначе можно получить лишние реакции, утечки памяти или обработку уже неактуального UI-сценария.

Для `entry`-компонентов удобный паттерн — привязывать подписку к `destroy$`:

```ts
import { takeUntil } from "rxjs";

this.context
  .watch()
  .pipe(takeUntil(this.destroy$))
  .subscribe((data) => {
    console.log("Контекст изменился:", data);
  });
```

Такой подход особенно полезен в `Page`, `Dialog` и других `entry`-компонентах: когда `entry.destroy$` срабатывает, подписка автоматически завершается.

Это один из самых частых сценариев:

- реакция на клик;
- submit формы;
- ответ от сервиса;
- загрузка следующих данных;
- серверная бизнес-логика.

## Способы инициализации `Context`

У `Context` есть три основных режима инициализации.

### 1. `preload`

```ts
context = createContext({
  preload: true,
  data: async () => ({
    draft: "",
  }),
});
```

`preload: true` заставляет BFF подготовить контекст заранее при авторизации клиента.

Это полезно, когда:

- данные точно нужны сразу;
- страница почти мгновенно опирается на этот контекст;
- вы не хотите ждать первого клиентского запроса к контексту.

### 2. Lazy-инициализация

```ts
context = createContext({
  data: async () => ({
    draft: "",
  }),
});
```

Если `preload` не указан, контекст инициализируется lazy: данные загружаются при первом клиентском запросе этого контекста (когда он потребуется для отображения компонента).

Это хороший вариант по умолчанию, когда:

- контекст может вообще не понадобиться;
- загрузка дорогая и не должна происходить заранее;
- вы хотите откладывать инициализацию до реального использования.

### 3. Ручной вызов `init()`

```ts
class ProfilePage extends Page {
  context = createContext({
    data: async () => ({
      name: "Alice",
    }),
  });

  override async boot() {
    await super.boot();
    await this.context.init();
  }

  protected title() {
    return "Профиль";
  }

  protected content() {
    const name = this.context.get("name");
    return [text(`Пользователь: ${name}`)];
  }
}
```

`boot()` — метод entry-компонента, здесь `ProfilePage`. BFF вызывает его до
сериализации страницы и до вызова `content()`. Поэтому ручной `init()` нужен,
когда загруженные данные контекста должны участвовать уже в построении разметки:
например, `content()` или `overlays()` вызывает `context.get()` либо строит
ветки и списки на основе полученных значений.

Если разметка использует только `context.ref()` и клиентские `conditions`, обычно
не нужно загружать значение вручную перед сериализацией.

### Практическое правило

- `preload` — когда данные точно нужны сразу;
- lazy — когда данные могут понадобиться позже;
- ручной `init()` в `boot()` — когда данные нужны серверу для построения
  `content()` или `overlays()` до отправки разметки клиенту.

## Валидация через `zod`

`schema` — список ключей, которые клиенту разрешено менять, и проверка типа значения. Входящее `context-values` обновляет только ключи из этой схемы.

Ключ обязательно описывают в `schema`, если его меняет клиент:

- компонент пишет значение в контекст. Сейчас это input'ы.
- ключ записан локальным действием `context.local` или `ref.local`.

Локальное действие сразу меняет зеркало контекста на клиенте и затем отправляет то же изменение на BFF сообщением `context-values`.

Ключ, который пишет только BFF (`data()`, `context.set`, `ref.set`, `replace`), в схему не включают. Тип такой записи проверяет TypeScript на сервере. Контекст, который клиент только читает, оставляют без `schema`.

### Почему привязка открывает весь контекст

Любая сериализованная ссылка на контекст привязывает клиента к этому контексту целиком: компонент, condition, плейсхолдер `@{…}`, payload локального действия. После привязки клиент получает полный snapshot и доступ к его редактированию.

Дальше он может прислать `context-values` по любому ключу этого контекста: значение другого типа или ключ, которого в данных нет. Типы input и `context.local.*` ограничивают только исходный код BFF. Сообщение с клиента они не проверяют.

Чтение ref (`text`, `when.equals` и другие conditions) само по себе запись не создаёт, но тоже открывает весь контекст. Серверные ключи в схему не добавляют: иначе клиент сможет записать в них значение подходящего типа.

Ключ вне `schema` входящим `context-values` не обновляется. Если `schema` не задана, входящее `context-values` отклоняется целиком. Значение, которое не проходит схему своего ключа, в контекст не попадает. В этих случаях ошибка уходит в стандартный поток ошибок клиента. Запись с BFF схему не проходит.

### Как описывать схему

Тип в Zod совпадает с тем, что контрол или local action реально отправляет:

- строковый input — `z.string()`, включая пустую строку;
- `numberInput`, `inc`, `dec` — `z.number()`;
- `toggle` — `z.boolean()`;
- `local.set` объекта или массива — та же форма, что в patch.

Вложенный путь (`user.email`, `items[0].qty`) описывают деревом `z.object` / `z.array`, чтобы путь существовал в схеме.

```ts
import { createContext } from "@matreshka/bff/core";
import { z } from "zod";

context = createContext({
  schema: z.object({
    query: z.string(),
    quantity: z.number(),
    enabled: z.boolean(),
  }),
  data: async () => ({
    query: "",
    quantity: 1,
    enabled: false,
    orderId: "srv-1",
    role: "viewer",
  }),
});

textInput(this.context.ref("query"));
button({ onClick: this.context.local.inc("quantity") }, [text("+")]);
button({ onClick: this.context.ref("enabled").local.toggle() }, [text("Вкл")]);

// orderId и role пишет только BFF
this.context.set({ role: "editor" });
```

Контекст только с серверными записями:

```ts
context = createContext({
  data: async () => ({ title: "Счёт", balance: 0 }),
});

text(this.context.ref("title"));
```

### Строгость на живом вводе

Схема здесь проверяет тип и то, что клиенту разрешено писать в ключ. Бизнес-правила вроде «это email» на поле, которое обновляется на каждый символ, часто слишком строгие.

Если схема требует `z.string().email()`, а пользователь ввёл только `test@`, значение не пройдёт проверку и не попадёт в `Context`.

Для живого ввода лучше:

- хранить в контексте более мягкий `draft` и проверять формат позже, например при submit;
- использовать схему, которая допускает промежуточные состояния ввода;
- разделять черновое значение и уже проверенное значение.

Это особенно важно для форм, фильтров и любого ввода, который возвращается с клиента. Формат, права и прочие бизнес-правила проверяйте в server handler.

## `strictRef()` и ссылки на другой контекст

В общем случае `ref()` может использоваться не только как ссылка на фиксированный путь, но и как основа для более сложного пути. Например, путь можно продолжать через другой `ref`. Однако такой способ нормально типизируется только в рамках одного и того же контекста, потому что TypeScript может строго вывести типы только пока речь идет об одном дереве данных.
Простой пример внутри одного контекста:

```ts
context = createContext({
  data: async () => ({
    userId: 1,
    users: [{ name: "Alice" }, { name: "Bob" }],
  }),
});

text(`Пользователь: ${this.context.ref("users").ref("userId").ref("name")}`);
```

Идея здесь такая: значение `userId` участвует в построении пути к `users[userId].name`, но все это происходит внутри одного и того же контекста.

Когда ссылка должна строиться через значение другого контекста, обычного `ref()` уже недостаточно. Здесь появляется `strictRef()`: он более строг к описанию типов контекстов, но зато позволяет безопасно строить кросс-контекстные ссылки.

То есть:

- обычный `ref()` хорошо подходит для путей внутри одного контекста;
- `strictRef()` нужен, когда путь в одном контексте зависит от значения, лежащего в другом контексте.

```ts
const cardsContext = createContext({
  data: async () => ({
    cards: [{ title: "A" }, { title: "B" }],
  }),
});

const indexContext = createContext({
  data: async () => ({ key: "0.title" }),
});

const dynamicCardTitleRef = cardsContext
  .ref("cards")
  .strictRef(indexContext.ref("key"));
```

Это advanced-сценарий, но он полезен, когда путь к данным должен определяться динамически.

## In-place mutation

Это скорее `bad practice`, а не основной рекомендуемый способ работы с контекстом.

Предпочитайте `set({ … })`, `ref.set(…)` или `replace` после load. Если собрали новое значение в локальной переменной:

```ts
const items = this.context.get("items") as Item[];
this.context.set({
  items: [...items, { id: "3", title: "Новый элемент" }],
});
```

`get` для объектов и массивов возвращает копию — мутация результата не меняет контекст, пока не вызван `set` / `replace`.

## Что приходит с клиента

Если в дерево для клиента попала хотя бы одна ссылка на контекст, клиент привязан ко всему этому контексту и может присылать `context-values`.

Честный клиент меняет ключ так:

- input пишет новое значение своего `ref`;
- `context.local` / `ref.local` пишет patch и синхронизирует его с BFF.

BFF применяет изменение только для ключей из `schema` и только после проверки типа. Нет схемы или ключ вне схемы — ошибка в поток ошибок клиента, контекст не меняется. Подписчики и остальные клиенты получают новое состояние только после успешной проверки.

Подробный протокол этих сообщений описан в [`../architecture/protocol.md`](../architecture/protocol.md).

## Уничтожение контекста

Состояние на BFF нужно **освобождать**, когда сценарий завершён: `context.destroy()` снимает запись из registry. **Уход со страницы при живой сессии сам контексты не удаляет** — для `Page` / `Dialog` обычно привязывают destroy к `stopUsing$`.

У **обычного** контекста (`persistent: false`) BFF **автоматически** вызывает `destroy()`, когда отвязан **последний** клиент. Ручной destroy раньше — **оптимизация по времени**, не «вечное» хранение: без клиентов контекст на сервере не остаётся. Флаг **`persistent: true`** отключает auto-destroy при нуле клиентов; тогда **критично** вызывать `destroy()` вручную, если данные не нужны весь runtime.

Сценарии (entry, client-scoped, `persistent`, свой компонент) — [Сценарии уничтожения Context](../advanced/context-destroy-scenarios.md). Протокол и holds — [Жизненный цикл Context](../architecture/context-lifecycle.md).
