# Компоненты: Сводка

Этот раздел посвящен именно компонентной модели matreshka: что общего у компонентов, чем отличаются `entry`-компоненты, как устроены `inputs`, `outputs`, `form`, `forEach`, `conditions` и `rules`.

Если нужен полный каталог всех существующих компонентов с перечислением свойств и примерами использования, смотрите [components-list.md](../reference/components-list.md).

## Общая идея

В matreshka UI собирается как дерево серверных компонентов. BFF создает экземпляры компонентов, сериализует их и отправляет клиенту.

Практически это означает:

- у каждого **инстанса** компонента на клиенте есть свой **instance id** (`uuid-0`, `uuid-1`, …);
- один BFF-объект `Component` имеет **базовый** id (часть до суффикса) и может быть сериализован несколько раз — каждый раз как **новый** инстанс с **одной** сериализацией;
- у каждого компонента есть свой `class`;
- компонент может иметь свойства, обработчики и условия отображения;
- клиент рендерит не JSX/HTML, а сериализованный конфиг компонента.

Подробнее — в [component-instance.md](../advanced/component-instance.md) (имеет смысл после [components-basics.md](components-basics.md) и [platforms.md](../reference/platforms.md)).

## Что общего у большинства компонентов

Все компоненты наследуются от базового `Component` и поддерживают общий набор возможностей.

### Общие свойства

У обычных компонентов есть базовые свойства:

- `colors` — цветовые роли компонента;
- `font` — стек шрифтов;
- `scale` — масштаб компонента;
- `textAlign` — выравнивание текста;
- `textDecoration` — оформление текста (`none`, `underline`, `line-through`);
- `gridItem` — настройки размещения внутри `grid`;
- `link` — ссылка, если компонент должен вести себя как переход.

Пример:

```ts
text(
  {
    scale: 2,
    textAlign: TextAlign.Center,
    textDecoration: TextDecoration.LineThrough,
  },
  "Крупный зачёркнутый текст",
);
```

### Общие обработчики

У компонентов есть два разных lifecycle-набора:

- regular-компоненты используют `onShow` / `onHide`;
- entry-компоненты (`Page`, `Dialog`, `Popover`) используют `onEnter` / `onLeave`.

Это не просто разные названия. `onShow` / `onHide` привязаны к обычным узлам дерева, которые могут появляться и исчезать из-за `conditions`, а `onEnter` / `onLeave` описывают жизненный цикл самостоятельного UI-контейнера.

И общие pointer-события наведения курсора:

- `onMouseEnter`
- `onMouseLeave`

Кроме этого, конкретные компоненты добавляют свои события. Например, у `stack` есть `onClick`, `onKeyDown`, `onScroll`.

## `conditions`

У компонентов есть `conditions` — условия, которые влияют на отображение компонента на клиенте.

Пример:

```ts
text(
  {
    conditions: [when.defined(this.context.ref("name"))],
  },
  "Имя заполнено",
);
```

Если условия не выполняются, компонент не отображается.

Важно: `conditions` относятся к обычным компонентам. У `entry`-компонентов логика другая, о ней ниже.

Полный каталог доступных условий — в [`conditions.md`](conditions.md).

## `rules`

`rules` — это условные переопределения свойств компонента. Если `conditions` решают, показывать компонент или нет, то `rules` решают, как именно он должен выглядеть при выполнении условий.

Пример:

```ts
button(
  {
    rules: [
      {
        conditions: [when.equals(this.context.ref("loading"), true)],
        overrides: {
          content: [text("Загрузка")],
        },
      },
    ],
  },
  [text("Отправить")],
);
```

Здесь кнопка отображается всегда, но когда `loading === true`, ее содержимое переопределяется на `"Загрузка"`.

`rules` особенно полезны для:

- адаптивности;
- loading/state-сценариев;
- локальных визуальных переопределений без ветвления дерева компонентов.

## `scale`

`scale` — это базовое свойство компонента, которое клиент использует как масштаб.

Важно не путать его с настройкой типографики. Если задача связана именно с размером текста, шрифтовой иерархией, `font-weight`, `line-height` и выбором гарнитуры, обычно правильнее использовать `fonts`. `scale` решает более общую задачу: меняет масштаб компонента целиком, включая связанные размеры, отступы, `gap` и другие пропорции, которые зависят от клиентского рендера этого компонента.

Практически `scale` полезен, когда нужно:

- сделать компонент визуально крупнее или компактнее целиком;
- быстро менять размерность компонента по условиям;
- переопределять размер через `rules`.

Пример:

```ts
text({ scale: 2 }, "Заголовок");
```

## `EntryComponent`

Отдельная категория — `entry`-компоненты. Это корневые или полу-корневые сущности, которые живут как самостоятельные точки входа в UI.

К ним относятся:

- `Page`
- `Dialog`
- `Popover`

Их особенность:

- они управляют собственным lifecycle;
- клиент регистрирует их как отдельные entry-узлы;
- у них есть `destroy()` и `destroy$`;
- в их init-конфиге нет `conditions`.

Публичный lifecycle у них такой:

- `onEnter` — entry впервые показан клиенту;
- `onLeave` — entry начал уходить, но ещё не уничтожен.

То есть `entry`-компонент — это не просто еще один leaf/branch в дереве, а самостоятельный UI-контейнер со своим жизненным циклом.

### Когда нужен `entry`-компонент

- `Page` — когда нужен основной экран;
- `Dialog` — когда нужен самостоятельный слой поверх страницы без якоря;
- `Popover` — когда нужен отдельный слой, привязанный к якорному компоненту.

## `Input`-компоненты

`Input`-компоненты работают через `ContextRef` и меняют данные в `Context`.

Общее для input-компонентов:

- они требуют `ref`;
- клиент отправляет изменения обратно в BFF;
- BFF обновляет `Context`.

Пример:

```ts
textInput(this.context.ref("name"));
```

Типичные `input`-компоненты:

- `textInput`
- `numberInput`
- `passwordInput`
- `textarea`
- `textEditor`

### Что у них общего

У всех input-компонентов есть одна общая идея: они не хранят данные сами по себе, а редактируют значение по `ref` в контексте.

## `Output`-компоненты

`Output`-компоненты отображают значение, но не редактируют его напрямую.

Они могут получать:

- статическое `value`;
- `ref`, если нужно читать значение из контекста.

Примеры:

```ts
text("Статический текст");
text(this.context.ref("name"));
text(`Привет, ${this.context.ref("name").toString()}`);
text({
  processors: [lineBreaks(), autolink()],
}, this.context.ref("content"));
number(42);
datetime(this.context.ref("createdAt"));
```

У `text()` также есть opt-in `processors`: они позволяют, например, превратить `\n` в переносы строк и сделать ссылки кликабельными, не включая парсинг для всего текстового вывода по умолчанию. Для таких ссылок можно отдельно задать `colors[ColorRole.Link]`.

Типичные `output`-компоненты:

- `text`
- `number`
- `currency`
- `datetime`
- `image`
- `iframe`
- `icon`
- `qrCode`
- `progressBar`
- `progressSpinner`

### Чем inputs отличаются от outputs

Коротко:

- `input` редактирует данные в `Context`;
- `output` отображает данные из `Context` или статическое значение.

## `form`

`form` — это специальный компонент для submit-сценариев. Он нужен не только для обработчика `onSubmit`, но и для корректной работы всей формы как UI-паттерна.

Почему это важно:

- пользователь может нажать `Enter` в поле;
- на мобильной клавиатуре обычно есть кнопка действия, например "Готово", "Далее" или "Отправить";

Пример:

```ts
const submitForm = () => {
  const name = this.context.value("name");
  this.context.setValue("result", `Привет, ${name}`);
};

form(
  {
    onSubmit: submitForm,
  },
  [
    textInput(this.context.ref("name")),
    button({ onClick: submitForm }, [text("Отправить")]),
  ],
);
```

Здесь `onClick` у кнопки не задает отдельную независимую логику, а намеренно дублирует поведение формы. Смысл в том, чтобы и submit формы, и явный клик по кнопке приводили к одному и тому же результату через общий обработчик `submitForm`.

Хороший паттерн:

- одну и ту же основную логику держать в общей функции;
- подключать ее в `onSubmit`;
- при необходимости повторно использовать в `onClick`.

## `forEach`

`forEach` — это специальный компонент для списков, завязанных на массив в `Context`.

Он нужен, когда:

- данные лежат в контексте как массив;
- для каждого элемента нужно построить один или несколько компонентов;
- нужен `track`, чтобы стабильно связывать данные и UI.

Под `track` здесь имеется в виду функция, которая возвращает устойчивый идентификатор элемента. Этот идентификатор нужен не просто "для порядка", а чтобы matreshka понимала, какой именно UI-элемент соответствует какой записи в массиве после обновлений.

Это особенно важно, когда список:

- дополняется;
- сортируется;
- фильтруется;
- частично перерисовывается;
- обновляется без полной замены всех элементов.

Если `track` выбран правильно, клиент может корректно сопоставить старые и новые элементы списка. Если выбран плохо, список может вести себя как полностью новый: у элементов будут сбрасываться локальные состояния, анимации, фокус или другие связанные эффекты.

Хорошие варианты для `track`:

- `item.id`
- `item.slug`
- другой стабильный бизнес-ключ, который не меняется между обновлениями

Плохие варианты:

- `Math.random()`
- текущее время
- индекс массива, если порядок элементов может меняться

Пример:

```ts
forEach({
  ref: this.context.ref("items"),
  track: (item) => item.id,
  generator: ({ ref }) => text(ref.ref("title")),
});
```

Что здесь важно:

- `ref` должен указывать на массив;
- `track` дает стабильный ключ и помогает matreshka не терять соответствие между данными и уже построенным UI;
- `generator` строит UI для каждого элемента.

Если **один и тот же** BFF-объект `forEach` вставлен в дерево несколько раз (две колонки, разные entry или клиенты), у каждого применения свой инстанс ForEach, свой кэш `generator` и свои дочерние инстансы. Подробный пример — в `component-instance.md`, раздел [ForEach: один объект — несколько мест на экране](../advanced/component-instance.md#foreach-один-объект--несколько-мест-на-экране).

### Когда `forEach` особенно полезен

- списки карточек;
- чаты;
- таблицы/ленты;
- динамические наборы полей;
- сценарии, где массив может меняться на сервере и должен синхронизироваться с клиентом.

## Практическое правило

Если нужно понять, как смотреть на компонент, обычно полезно задать три вопроса:

1. Это `entry` или обычный компонент?
2. Это layout, input, output или специальный компонент?
3. Нужны ли ему `conditions`, `rules`, `scale` и `ContextRef`?

После этого структура компонента обычно становится понятной намного быстрее.
