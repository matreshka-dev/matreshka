# WebMCP

WebMCP позволяет ИИ-агенту выполнять действия в открытом интерфейсе приложения: получать данные, заполнять формы, открывать диалоги, запускать команды устройства и выполнять другие операции.

В Matreshka такие действия называются **инструментами** (tools). Вы объявляете их на BFF, а клиент передаёт доступные инструменты браузерному агенту. Когда агент вызывает инструмент, запрос приходит на BFF и запускает его функцию `execute`.

У каждого инструмента есть:

- `name` — уникальное понятное имя, по которому агент выбирает действие;
- `description` — объяснение, для чего нужен инструмент;
- `inputSchema` — необязательная Zod-схема аргументов;
- `execute` — асинхронная функция на BFF, которая выполняет действие и возвращает текстовый результат;
- `annotations` и `conditions` — необязательные подсказки о характере действия и условия его доступности.

Главная идея: **описание инструмента объясняет агенту, когда его вызывать, схема аргументов — какие данные передать, а `execute` — что именно сделать.**

## Где объявлять инструменты

Инструменты можно объявить на конкретном элементе интерфейса (entry) или на клиентской платформе целиком.

### На странице

Переопределите метод `tools()` в классе страницы:

```ts
import { Page, text, webMcpTool, WebMcpToolAnnotation } from "@matreshka/bff";

export class OrdersPage extends Page {
  protected title() {
    return "Заказы";
  }

  protected content() {
    return [text("Список заказов")];
  }

  protected tools() {
    return [
      webMcpTool({
        name: "get_order_status",
        description: "Показывает текущий статус заказа",
        annotations: [WebMcpToolAnnotation.ReadOnlyHint],
        execute: async () => "Заказ №123 находится в пути.",
      }),
    ];
  }
}
```

Пока страница открыта, её инструменты могут быть доступны агенту. Когда страница закрывается, клиент убирает их.

### В диалоге или popover

Передайте инструменты в конфигурации диалога или popover:

```ts
dialog({
  tools: [
    webMcpTool({
      name: "confirm_order",
      description: "Подтверждает оформление заказа",
      annotations: [WebMcpToolAnnotation.ConsequentialHint],
      execute: async () => "Заказ подтверждён.",
    }),
  ],
  content: [text("Подтвердите оформление заказа")],
});
```

Инструменты такого entry доступны, пока соответствующий диалог или popover открыт.

`webMcpTool({ ... })` — рекомендуемый способ создания инструмента. `new WebMcpTool({ ... })` создаёт такой же объект, поскольку это тот же класс.

## Глобальные инструменты

Если действие должно быть доступно независимо от открытой страницы, объявите его на клиентской платформе:

```ts
import { currentClientPlatform, webMcpTool } from "@matreshka/bff";
import { firstValueFrom } from "rxjs";

await firstValueFrom(
  currentClientPlatform().setTools([
    webMcpTool({
      name: "get_device_location",
      description: "Запрашивает геолокацию устройства и возвращает координаты",
      execute: async () => "Координаты: 55.75, 37.62",
    }),
  ]),
);
```

Вызов `setTools()` **заменяет весь предыдущий список глобальных инструментов**. Передайте `[]`, чтобы убрать глобальные инструменты. При этом инструменты открытой страницы или диалога останутся доступны.

Получить текущий глобальный список можно через `getTools()`.

## Имя инструмента

Имя — один из главных ориентиров, по которым агент выбирает действие. Поэтому оно должно быть коротким, понятным и описывать конкретное действие.

Допустимы только латинские буквы, цифры, дефис и подчёркивание. После удаления пробелов по краям имя должно соответствовать шаблону:

```ts
/^[A-Za-z0-9_-]+$/;
```

Например:

```ts
name: "get_order_status"; // правильно
name: "get-order-status"; // правильно
name: "fillNote2"; // правильно

name: "Получить статус"; // неправильно: кириллица и пробел
name: "get order status"; // неправильно: пробел внутри
name: "order.status"; // неправильно: точка
```

Старайтесь не использовать одинаковые имена у одновременно доступных инструментов. На сервере у таких инструментов могут быть разные внутренние идентификаторы, но в браузере имя должно быть уникальным. Если возникнет конфликт, клиент добавит суффикс: `save`, `save_2`, `save_3`. Агенту будет сложнее понять, какой из вариантов нужен.

## Аргументы инструмента

Если агенту нужно передать данные, задайте `inputSchema` с помощью **Zod 4**:

```ts
import { z } from "zod";

webMcpTool({
  name: "add_todo",
  description: "Добавляет задачу в список дел",
  inputSchema: z.object({
    text: z.string().describe("Текст новой задачи."),
  }),
  execute: async (input) => {
    return `Задача «${input.text}» добавлена.`;
  },
});
```

TypeScript выведет тип `input` из Zod-схемы. В этом примере `input` имеет тип `{ text: string }`.

Matreshka преобразует Zod-схему в JSON Schema и передаёт её клиенту. Агент видит описание полей и использует его, чтобы сформировать аргументы. Когда агент вызывает инструмент:

1. аргументы приходят на BFF;
2. BFF проверяет их по `inputSchema`;
3. если данные не соответствуют схеме, `execute` не запускается, а агент получает сообщение об ошибке;
4. если проверка прошла, аргументы передаются в `execute`.

Если `inputSchema` не задана, `execute` вызывается без аргументов.

### Описывайте значения так, чтобы агент мог выбрать их правильно

Одного типа данных часто недостаточно. Например, `z.number()` сообщает агенту, что нужно передать число, но не объясняет, какое число соответствует нужному пункту интерфейса.

В `.describe()` указывайте смысл значения и допустимые варианты. Описание должно помогать выбрать значение, а не объяснять внутреннее устройство приложения.

Особенно внимательно описывайте поля, которые затем попадают в `Context`. Посмотрите, откуда пользователь может получить или изменить это значение:

- начальные данные контекста (`data()`);
- контролы, привязанные к тому же `ref`;
- обработчики кнопок, submit и другие обработчики, меняющие это поле;
- подписи, placeholder и варианты выбора рядом с контролом.

Используйте те же значения и подписи, что и в интерфейсе. Если в селекте пользователь видит «Курьер», агенту нужно объяснить, какой `id` соответствует этому варианту.

Если список вариантов известен при создании инструмента, ограничьте аргумент допустимыми значениями через `z.literal`. Тогда в JSON Schema будет передан `enum`, и агент не сможет выбрать произвольный идентификатор.

### Пример: выбор значения из селекта

Представим, что на странице есть селект «Тип доставки». В интерфейсе пользователь видит подписи, а в контексте хранится числовой `typeId`.

```ts
const deliveryTypes = [
  { id: 1, label: "Курьер" },
  { id: 2, label: "Самовывоз" },
  { id: 3, label: "Пункт выдачи" },
] as const;

// Этот же массив используйте для построения вариантов селекта.
const typeIds = deliveryTypes.map((item) => item.id);
const typeIdOptions = deliveryTypes
  .map((item) => `${item.id} — «${item.label}»`)
  .join("; ");

webMcpTool({
  name: "set_delivery_type",
  description: "Выбирает тип доставки. Заказ при этом не оформляется.",
  inputSchema: z.object({
    typeId: z
      .literal(typeIds)
      .describe(`Тип доставки. Допустимые значения: ${typeIdOptions}.`),
  }),
  execute: async (input) => {
    await lastValueFrom(this.context.set({ typeId: input.typeId }));

    const label = deliveryTypes.find((item) => item.id === input.typeId)?.label;

    return `Выбран тип доставки «${label}».`;
  },
});
```

Здесь описание объясняет соответствие между числом и подписью в интерфейсе. Сам массив вариантов используется и для UI, и для схемы инструмента — так меньше риск, что они разойдутся.

Неудачный вариант:

```ts
webMcpTool({
  name: "Выбрать тип",
  description: "Ставит тип",
  inputSchema: z.object({
    typeId: z.number(),
  }),
  execute: async (input) => {
    this.context.set({ typeId: input.typeId });
    return "ok";
  },
});
```

Здесь имя не соответствует допустимому формату, а `z.number()` не объясняет, какие значения разрешены и что они означают.

### Что писать в `.describe()`

Ориентируйтесь на тип поля:

- **Идентификатор или enum:** перечислите допустимые значения и их подписи. Если варианты известны заранее, ограничьте их через `z.literal`.
- **Число:** укажите назначение, единицу измерения, минимум, максимум и шаг, если они есть.
- **Строка:** объясните, что именно нужно передать, и укажите формат. Если это обычный текст, скажите об этом, чтобы агент не принял его за идентификатор.
- **Дата и время:** укажите ожидаемый формат; если требуется ISO 8601 с часовым поясом, напишите это явно.
- **Boolean:** объясните, что означает `true` и что означает `false`, используя понятные пользователю формулировки.

Разделяйте два уровня описания:

- `description` инструмента отвечает на вопрос **«Зачем и когда вызывать это действие?»**
- `.describe()` поля отвечает на вопрос **«Какое значение нужно передать?»**

Не нужно писать в описаниях про `Context`, BFF, `ref` и внутренний способ сохранения данных. Это детали реализации, которые не помогают агенту выбрать правильное значение.

## Подсказки о характере действия

Свойство `annotations` позволяет сообщить агенту и браузеру, что делает инструмент и насколько действие чувствительно.

| Подсказка              | Когда использовать                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------- |
| `ReadOnlyHint`         | Инструмент только читает данные и ничего не меняет. Например, получает статус заказа.               |
| `UntrustedContentHint` | Результат содержит чужие или непроверенные данные, например текст из пользовательского комментария. |
| `ConsequentialHint`    | Инструмент выполняет значимое действие: оплачивает заказ, удаляет данные, оформляет бронирование.   |
| `Debugging`            | Инструмент предназначен для отладки, а не для обычного пользовательского сценария.                  |

Подсказки необязательны. Если значение не указано, соответствующая подсказка считается выключенной.

Не помечайте действие как `ReadOnlyHint`, если оно меняет данные или состояние интерфейса. Если инструмент одновременно читает данные и выполняет значимое действие, выбирайте аннотации, которые честно описывают его поведение.

## Условия видимости

Свойство `conditions` определяет, когда инструмент должен быть доступен агенту. Оно использует те же условия, что и компоненты и действия: `when` и `device`.

Например, инструмент сохранения черновика нужен только в режиме редактирования:

```ts
protected tools() {
  return [
    webMcpTool({
      name: "save_draft",
      description: "Сохраняет текущий черновик",
      conditions: [
        when.equals(this.context.ref("mode"), "edit"),
      ],
      execute: async () => {
        await this.saveDraft();
        return "Черновик сохранён.";
      },
    }),
  ];
}
```

Пока условие выполняется, клиент показывает инструмент агенту. Когда условие перестаёт выполняться, клиент убирает его.

Несколько условий в массиве означают логическое **«И»**: все условия должны выполниться. Для логики **«ИЛИ»** используйте `when.any()` и `when.all()` — подробнее в разделе [Conditions](conditions.md).

**Важно:** `conditions` управляет только видимостью инструмента. BFF не проверяет эти условия повторно при вызове. Если действие разрешено не всегда, обязательно проверьте актуальное состояние внутри `execute` — например, что заказ ещё можно отменить или пользователь имеет нужные права.

## Что делает `execute` и что получает агент

`execute` — обычная асинхронная функция, которая выполняется на BFF. Её результат должен быть строкой. Эту строку агент получает как ответ на вызов инструмента.

Пишите результат так, чтобы он был понятен без знания внутреннего устройства приложения:

```ts
return "Заказ №123 создан. Статус: «Новый».";
```

Не ограничивайтесь техническими ответами вроде `"ok"`, `"true"` или `"done"`. Лучше сообщить, что именно произошло, и добавить полезные данные: номер, статус или выбранный вариант.

Если `execute` выбрасывает ошибку, агент получает текст ошибки. Поэтому текст должен объяснять проблему понятным языком и, по возможности, подсказывать, что можно сделать дальше.

```ts
webMcpTool({
  name: "create_delivery_request",
  description: "Создаёт заявку на доставку",
  inputSchema: z.object({
    comment: z.string().describe("Комментарий к заявке."),
  }),
  execute: async (input) => {
    try {
      const request = await this.requests.create(input.comment);
      return `Заявка №${request.number} создана. Статус: «Новая».`;
    } catch (error) {
      if (error instanceof AddressOutsideZoneError) {
        throw new Error("Доставка по этому адресу недоступна.");
      }

      if (error instanceof SlotTakenError) {
        throw new Error(
          "Выбранное время доставки уже занято. Выберите другое время.",
        );
      }

      throw new Error("Не удалось создать заявку. Попробуйте ещё раз.");
    }
  },
});
```

Преобразуйте внутренние ошибки в понятные сообщения. Не отправляйте агенту stack trace, SQL-ошибки и другие технические подробности. Если ошибка уже пришла от команды платформы и её текст понятен пользователю, его можно передать без изменений.

Изменение данных на экране не происходит автоматически от самого факта вызова инструмента. Если нужно обновить UI, сделайте это в `execute` — например, через `Context`, `ref` или команды компонентов.

## Дождитесь, пока клиент выполнит действие

Это важная особенность WebMCP в Matreshka.

`execute` работает на BFF, а интерфейс находится в браузере. Поэтому вызов может отправить команду клиенту, но не дождаться, пока браузер её выполнит. Если вернуть результат сразу, агент может сообщить об успехе раньше, чем пользователь увидит изменения на экране.

**Если результат инструмента зависит от изменения интерфейса или команды устройства, дождитесь подтверждения от клиента перед `return`.**

### Команды платформы

Методы клиентской платформы возвращают `Observable`. Обычно его нужно преобразовать в Promise с помощью `firstValueFrom`:

```ts
import { currentClientPlatform, webMcpTool } from "@matreshka/bff";
import { firstValueFrom } from "rxjs";

webMcpTool({
  name: "get_device_location",
  description: "Запрашивает геолокацию устройства и возвращает координаты",
  execute: async () => {
    const platform = currentClientPlatform();

    const { latitude, longitude } = await firstValueFrom(
      platform.getGeolocation(),
    );

    return `Координаты устройства: ${latitude}, ${longitude}.`;
  },
});
```

`firstValueFrom` ждёт первого результата Observable. В этом примере функция `execute` не завершится, пока браузер не обработает запрос геолокации и не вернёт координаты.

Если пользователь запретит доступ или браузер не сможет определить местоположение, Observable завершится ошибкой. Она выйдет из `execute`, и агент получит сообщение об ошибке. Отдельный `catch` нужен только в том случае, если вы хотите преобразовать эту ошибку в собственное сообщение.

Тот же подход применим к другим командам платформы: открытию диалога, скачиванию файла, переходу на другую страницу и другим действиям. Выбирайте момент ожидания в соответствии с тем, что означает завершение конкретной команды. Например, `showDialog()` завершается после монтирования диалога, а не после того, как пользователь его закрыл.

Список команд смотрите в [Platform API](../reference/platforms.md).

### Доставка изменений Context и ref

`context.set()` и `ref.set()` также возвращают `Observable`. Он сообщает о доставке новых значений клиентам: в поле `delivered` перечислены клиенты, которые уже получили обновление.

Если контекст используется только одним клиентом, можно дождаться завершения доставки всем получателям через `lastValueFrom`:

```ts
import { lastValueFrom } from "rxjs";

await lastValueFrom(
  this.context.set({
    title: input.title,
    text: input.text,
  }),
);
```

Если контекст может быть подключён к нескольким клиентам, а нужно дождаться обновления именно того клиента, который вызвал инструмент, отфильтруйте событие по текущему клиенту:

```ts
import { currentClient } from "@matreshka/bff";
import { filter, firstValueFrom } from "rxjs";

const client = currentClient();

await firstValueFrom(
  this.context
    .set({ title: input.title })
    .pipe(filter(({ delivered }) => delivered.includes(client))),
);
```

`firstValueFrom` здесь завершится, когда нужный клиент появится в `delivered`. Это позволяет не ждать всех клиентов.

Подробнее о доставке изменений читайте в разделе [Context](context.md).

## Пример: агент заполняет и сохраняет заметку

Пусть на странице есть два поля — заголовок и текст заметки. Пользователь может заполнить их сам, а агент — вызвать инструмент `save_note` с нужными значениями.

В этом сценарии агент не просто меняет интерфейс: он также сохраняет заметку. Поэтому `execute` должен дождаться доставки значений в контекст, выполнить сохранение и вернуть понятный результат.

```ts
import { createContext, Page, textInput, textarea, webMcpTool } from "@matreshka/bff";
import { lastValueFrom } from "rxjs";
import { z } from "zod";

type NoteState = {
  title: string;
  text: string;
};

export class NotePage extends Page {
  context = createContext({
    schema: z.object({
      title: z.string(),
      text: z.string(),
    }),
    data: async () => ({
      title: "",
      text: "",
    }),
  });

  protected async boot() {
    await this.context.init();
  }

  protected title() {
    return "Заметка";
  }

  protected content() {
    return [
      textInput({ placeholder: "Заголовок" }, this.context.ref("title")),
      textarea({ placeholder: "Текст" }, this.context.ref("text")),
    ];
  }

  protected tools() {
    return [
      webMcpTool({
        name: "save_note",
        description: "Заполняет заголовок и текст заметки и сохраняет её",
        inputSchema: z.object({
          title: z.string().describe("Заголовок заметки."),
          text: z.string().describe("Полный текст заметки."),
        }),
        execute: async (input) => {
          await lastValueFrom(
            this.context.set({
              title: input.title,
              text: input.text,
            }),
          );

          await this.saveNote(input);

          return `Заметка «${input.title}» сохранена.`;
        },
      }),
    ];
  }

  private async saveNote(note: NoteState) {
    // Здесь выполните запрос в базу данных или ваш API.
  }
}
```

Обратите внимание на порядок действий:

1. `context.set()` отправляет новые значения в поля.
2. `lastValueFrom()` дожидается доставки изменений всем получателям контекста.
3. `saveNote()` сохраняет заметку.
4. `return` сообщает агенту об успешном сохранении.

Если сохранение завершится ошибкой, не возвращайте сообщение об успехе: преобразуйте ошибку в понятный текст и выбросьте её.

## Пример: агент заполняет форму, но сохраняет пользователь

Иногда агенту нужно только подготовить данные, а окончательное действие должен подтвердить человек. Например, агент заполняет форму заметки, а пользователь проверяет её и нажимает кнопку «Сохранить».

В таком сценарии инструмент не должен вызывать `saveNote()`. Он должен дождаться, пока поля действительно обновятся в браузере, и сообщить агенту, что осталось сделать пользователю.

```ts
import {
  button,
  text,
  textInput,
  textarea,
  webMcpTool,
} from "@matreshka/bff";
import { currentClient } from "@matreshka/bff";
import { filter, firstValueFrom } from "rxjs";
import { z } from "zod";

protected content() {
  return [
    textInput(
      { placeholder: "Заголовок" },
      this.context.ref("title"),
    ),
    textarea(
      { placeholder: "Текст" },
      this.context.ref("text"),
    ),
    button(
      {
        onClick: () =>
          this.saveNote({
            title: this.context.get("title"),
            text: this.context.get("text"),
          }),
      },
      [text("Сохранить")],
    ),
  ];
}

protected tools() {
  return [
    webMcpTool({
      name: "fill_note",
      description: "Заполняет поля заметки, но не сохраняет её",
      inputSchema: z.object({
        title: z.string().describe("Заголовок заметки."),
        text: z.string().describe("Полный текст заметки."),
      }),
      execute: async (input) => {
        const client = currentClient();

        await firstValueFrom(
          this.context
            .set({
              title: input.title,
              text: input.text,
            })
            .pipe(
              filter(({ delivered }) => delivered.includes(client)),
            ),
        );

        return "Поля заметки заполнены. Проверьте заголовок и текст, затем нажмите «Сохранить».";
      },
    }),
  ];
}
```

Здесь используется `firstValueFrom` с фильтром по текущему клиенту: инструмент ждёт обновления именно в браузере пользователя, который вызвал действие. Только после доставки он возвращает результат агенту.

Такой подход подходит для действий, после которых человек должен проверить данные или дать согласие: заполнить форму, подготовить платёж, составить заявку, но не отправлять её.

## Пример: открыть диалог и заполнить его

Команды платформы можно объединять в одну последовательную цепочку. Например, сначала открыть диалог, дождаться его монтирования, затем заполнить поле и дождаться доставки значения в браузер.

```ts
import {
  currentClient,
  currentClientPlatform,
  webMcpTool,
} from "@matreshka/bff";
import { filter, firstValueFrom } from "rxjs";

webMcpTool({
  name: "open_request_dialog",
  description: "Открывает диалог заявки и подставляет комментарий",
  inputSchema: z.object({
    comment: z.string().describe("Комментарий к заявке."),
  }),
  execute: async (input) => {
    const platform = currentClientPlatform();
    const client = currentClient();
    const requestDialog = new RequestDialog();

    // Дождаться, пока диалог появится в интерфейсе.
    await firstValueFrom(platform.showDialog(requestDialog));

    // После монтирования диалога заполнить поле и дождаться его доставки.
    await firstValueFrom(
      requestDialog.context
        .set({ comment: input.comment })
        .pipe(filter(({ delivered }) => delivered.includes(client))),
    );

    return "Диалог заявки открыт, комментарий заполнен. Проверьте данные и отправьте заявку.";
  },
});
```

Не пытайтесь заполнить контекст диалога до его открытия, если для доставки требуется уже смонтированный клиентский компонент. Сначала дождитесь `showDialog()`, затем меняйте контекст.
