# Валидация изменений Context

## Зачем нужна валидация

В Matreshka BFF данные интерфейса хранятся в `Context`. Компоненты могут читать значения контекста, изменять их и синхронизировать изменения с сервером.

При разработке приложения типы данных проверяются TypeScript. Например, если `name` — строка, то `textInput` не позволит привязать к нему значение другого типа.

Однако TypeScript работает только на этапе разработки. Он не проверяет данные, которые фактически приходят в приложение извне. Источником таких данных может быть клиент, сторонний API, внешний сервис или другой ресурс, которому нельзя безусловно доверять.

Поэтому данные из недоверенных источников нужно проверять во время выполнения с помощью Zod.

Основная идея проста:

- данные, поступающие из недоверенных источников, проходят runtime-валидацию;
- внутренние изменения, формируемые самим серверным кодом, могут опираться на TypeScript-типизацию.

Клиент — один из таких недоверенных источников, но не единственный. Валидация защищает не только от намеренно некорректных сообщений, но и от неожиданных форматов, изменений API и ошибок интеграций.

## Как клиент получает доступ к Context

Context — это единое хранилище данных, которое может использоваться разными компонентами и конструкциями интерфейса.

Например, компонент может получать ссылку на конкретное значение:

```typescript
textInput({
  ref: this.context.ref("name"),
});
```

Но передача ссылки на отдельный ключ не означает, что клиент получает доступ только к нему.

Когда интерфейс использует Context через компонент, condition или другую конструкцию, содержащую ссылку на него, клиент получает snapshot всего этого Context.

Это важно учитывать при проектировании структуры данных.

### Пример

Предположим, на сервере создан контекст:

```typescript
context = new Context({
  data: async () => ({
    name: "Дмитрий",
    age: 30,
    role: "admin",
    userId: 123,
  }),
});
```

В интерфейсе используется только одно поле:

```typescript
textInput({
  ref: this.context.ref("name"),
});
```

Несмотря на то что компонент работает только с `name`, клиент получает весь snapshot:

```json
{
  "name": "Дмитрий",
  "age": 30,
  "role": "admin",
  "userId": 123
}
```

Таким образом, наличие ссылки на один ключ открывает клиенту доступ ко всему соответствующему Context.

## Почему TypeScript недостаточно

При разработке типизация защищает от большинства ошибок внутри приложения.

Например:

```typescript
context = new Context({
  data: async () => ({
    name: "",
    age: 0,
  }),
});

textInput({
  ref: this.context.ref("name"),
});

numberInput({
  ref: this.context.ref("age"),
});
```

TypeScript позволяет связать `textInput` со строковым значением, а `numberInput` — с числовым.

Но TypeScript не гарантирует корректность данных, пришедших извне.

Клиент не является доверенной средой: пользователь может самостоятельно сформировать сетевое сообщение, не используя штатные компоненты Matreshka. Аналогичная проблема возникает при интеграции со сторонним API: его ответ может измениться, содержать неожиданные значения или не соответствовать документации.

Например, вместо ожидаемого значения:

```json
{
  "name": "Дмитрий"
}
```

клиент может отправить:

```json
{
  "name": 123
}
```

Или попытаться изменить совершенно другой ключ:

```json
{
  "role": "user"
}
```

TypeScript не участвует в обработке таких сообщений. Поэтому серверу необходим собственный механизм проверки входящих изменений.

## Как работает Zod-схема

Для runtime-валидации в контексте предусмотрено поле `schema`.

Схема описывает структуру и типы данных, которые нужно проверять на границе с недоверенным источником. В частности, она определяет ключи Context, которые разрешено изменять клиенту, и проверяет типы поступающих значений.

На этапе компиляции тип данных и Zod-схема связываются через `ContextSchema<T, S>`: схема может описывать все поля или только часть, но не может содержать лишних ключей или несовместимых типов. Контекст создаётся функцией `context({ data, schema?, … })` — TypeScript выведет `T` из `data` и тип схемы из `schema`. Если в первом ответе `data` нет части полей модели (например опциональных), задайте тип явно на колбэке: `data: async (): Promise<MyT> => (…))`.

Например:

```typescript
pageContext = context({
  schema: z.object({
    name: z.string(),
    age: z.number(),
  }),

  data: async () => ({
    name: "",
    age: 0,
    role: "admin",
  }),
});
```

Теперь сервер располагает явным описанием допустимых клиентских изменений:

| Ключ   | Тип    | Клиентская запись       |
| ------ | ------ | ----------------------- |
| `name` | string | Разрешена               |
| `age`  | number | Разрешена               |
| `role` | string | Не предусмотрена схемой |

Таким образом, схема выполняет две связанные задачи:

1. Проверяет структуру и типы данных, поступающих из недоверенного источника.
2. Для клиентских обновлений определяет, какие ключи Context разрешено изменять, и проверяет значения этих ключей.

При этом наличие ключа в `schema` само по себе не запрещает серверному коду изменять другие ключи Context.

### Отклонение недопустимого изменения

Сервер применяет входящее `context-values` только после проверки.

- Если у контекста нет `schema`, изменение отклоняется: данные не меняются, ошибка уходит в поток ошибок клиента.
- Если ключ не описан в `schema`, происходит то же самое. Сообщение с несколькими полями не применяется частично: один ключ вне схемы отменяет весь patch.
- Если ключ описан, но значение не проходит тип, Zod бросает ошибку, и значение в контекст не попадает.

Серверные `set`, `replace` и `data()` эту проверку не проходят.

## Какие изменения требуют схемы

Не каждое использование Context означает, что клиент может изменять его значения. При этом клиентские обновления — лишь один из сценариев, в которых нужна runtime-валидация.

Удобно различать два случая.

### Данные от клиента

К этой группе относятся операции, при которых клиент локально изменяет значение, а затем отправляет изменение серверу для синхронизации.

**1. Input-компоненты**

Например:

```typescript
textInput({
  ref: this.context.ref("name"),
});

numberInput({
  ref: this.context.ref("age"),
});

textarea({
  ref: this.context.ref("description"),
});
```

В этом случае все три ключа должны присутствовать в `schema`.

**2. Локальные команды Context**

Matreshka позволяет изменять значения непосредственно через локальные команды:

```typescript
this.context.local.inc("quantity");

this.context.local.toggle("enabled");

this.context.local.set("name", "Новое имя");
```

Аналогичные операции доступны через `ref.local`:

```typescript
this.context.ref("enabled").local.toggle();

this.context.ref("name").local.set("Новое имя");
```

Поскольку эти изменения также синхронизируются с сервером, соответствующие ключи должны быть описаны в Zod-схеме.

### Данные из доверенного серверного кода

Если значение формируется внутренним серверным кодом, серверные операции не требуют наличия ключей в `schema`: здесь можно полагаться на TypeScript-типизацию.

Например:

```typescript
this.context.set({
  role: "admin",
});

this.context.ref("status").set("approved");
```

К этой же группе относятся первоначальное заполнение через `data()` и замена данных через `replace()`.

Для таких операций сохраняется обычная TypeScript-типизация.

### Данные от стороннего API

Серверный код тоже может получать данные, которым нельзя доверять. Например, приложение запрашивает сведения о доставке у внешнего API. Даже если у API есть документация и TypeScript-типы для клиента интеграции, фактический HTTP-ответ остаётся внешними данными: сервис может вернуть `null` вместо строки, изменить формат поля или прислать неполный объект.

Перед тем как использовать такой ответ в Context, его нужно проверить через Zod-схему:

```typescript
const deliverySchema = z.object({
  status: z.enum(["pending", "shipped", "delivered"]),
  trackingNumber: z.string(),
});

context = new Context({
  schema: deliverySchema,

  data: async () => ({
    status: "pending",
    trackingNumber: "",
  }),
});

// Получаем ответ от внешнего сервиса
const response = await fetch(deliveryApiUrl);
const payload: unknown = await response.json();

// Проверяем фактические данные во время выполнения
const delivery = context.schema.parse(payload);

// Только после успешной проверки используем данные
this.context.set(delivery);
```

Если ответ не соответствует схеме, `parse()` выбросит ошибку в месте получения данных. Это позволяет обработать некорректный ответ интеграции сразу, а не получить трудно диагностируемую runtime-ошибку позже — например, при обращении к отсутствующему полю в компоненте.

**Важно:** в текущей модели `Context` ключи, описанные в `schema`, также относятся к ключам, разрешённым для клиентской записи. Поэтому включайте в такую схему данные стороннего API только в том случае, если клиенту действительно допустимо изменять эти поля. Если API возвращает серверные поля, которые клиент не должен менять, для них используйте отдельную Zod-схему проверки ответа и не расширяйте ради них клиентскую write-схему.

### Чтение значений

Само по себе чтение значения не требует добавления ключа в `schema`.

Например:

```typescript
text(this.context.ref("name"));
```

Здесь компонент только отображает значение. Клиент не изменяет его.

## Совместное использование клиентских и серверных изменений

Довольно часто один Context содержит данные, которые изменяются с разных сторон.

Например, в форме редактирования профиля пользователь может менять имя, а сервер самостоятельно управляет статусом профиля.

```typescript
context = new Context({
  schema: z.object({
    name: z.string(),
  }),

  data: async () => ({
    name: "",
    status: "draft",
  }),
});

// Клиент изменяет имя
textInput({
  ref: this.context.ref("name"),
});

// Сервер изменяет статус
this.context.set({
  status: "approved",
});
```

В этом случае в `schema` присутствует только `name`.

`status` не требует Zod-валидации входящих клиентских изменений, поскольку не предназначен для клиентской записи.

Если один и тот же ключ изменяется и клиентом, и сервером, он всё равно должен присутствовать в `schema`. Наличие ключа в схеме не ограничивает серверные операции.

## Пример полноценного Context

Рассмотрим форму заказа.

Пользователь может изменять количество товаров и комментарий. Итоговая стоимость и статус заказа рассчитываются сервером.

```typescript
context = new Context({
  schema: z.object({
    quantity: z.number(),
    comment: z.string(),
  }),

  data: async () => ({
    quantity: 1,
    comment: "",
    total: 1500,
    status: "new",
  }),
});

// Количество изменяется локально
numberInput({
  ref: this.context.ref("quantity"),
});

// Комментарий изменяется через input
textarea({
  ref: this.context.ref("comment"),
});

// Итоговая стоимость обновляется сервером
this.context.set({
  total: 3000,
  status: "processing",
});
```

Распределение ответственности:

| Поле       | Кто изменяет | Zod-схема    |
| ---------- | ------------ | ------------ |
| `quantity` | Клиент       | `z.number()` |
| `comment`  | Клиент       | `z.string()` |
| `total`    | Сервер       | Не требуется |
| `status`   | Сервер       | Не требуется |

Такой подход позволяет не дублировать серверную типизацию в Zod-схеме для всех полей Context, а описывать только те данные, которые действительно могут поступать от клиента.

## Вложенные структуры

Если клиент изменяет вложенные значения, их структура также описывается в схеме.

Например, для профиля пользователя:

```typescript
context = new Context({
  schema: z.object({
    user: z.object({
      name: z.string(),
      email: z.string(),
    }),
  }),

  data: async () => ({
    user: {
      name: "",
      email: "",
    },
  }),
});
```

Здесь `user.name` и `user.email` относятся к клиентским изменениям.

Для массивов используются `z.array()` и соответствующие схемы элементов.

Конкретная структура схемы должна соответствовать формату обновлений, который использует механизм синхронизации Context. В частности, важно учитывать, как обрабатываются частичные изменения вложенных объектов.

## Важное замечание о данных Context

Поскольку клиент получает snapshot всего Context, его структура влияет не только на синхронизацию, но и на доступность данных.

Наличие или отсутствие ключа в `schema` не определяет, увидит ли клиент его значение.

Например, `role` может отсутствовать в схеме, но если он присутствует в snapshot, клиент всё равно получит его.

Поэтому данные, которые не должны быть доступны клиенту, не следует хранить в сериализуемом клиенту Context.

## Итог

Модель валидации Context строится на разделении ответственности:

- **TypeScript** обеспечивает типизацию внутреннего кода приложения.
- **Zod** проверяет данные на границе с недоверенными источниками.
- Для клиентских обновлений `schema` дополнительно определяет ключи, которые клиенту разрешено изменять.

Ключевой момент — не то, где физически выполняется код, а насколько можно доверять источнику данных.

Если данные пришли от клиента или стороннего сервиса, их следует проверить во время выполнения до использования в приложении. Если значение сформировано внутренним серверным кодом, обычно достаточно TypeScript-типизации.

Такое разделение позволяет сохранить гибкость Context и не заставляет описывать в Zod-схеме все данные без разбора.
