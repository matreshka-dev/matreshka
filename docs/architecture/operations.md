# Эксплуатация и ограничения

matreshka удобно использовать как BFF-инструмент, но у этой архитектуры есть важные операционные особенности. Этот раздел помогает не столкнуться с ними слишком поздно.

## Главное ограничение: состояние живет в памяти BFF

matreshka хранит клиентов в памяти процесса:

- каждому token соответствует `Client`;
- у `Client` есть `state$`, handlers, scoped components и entry-компоненты;
- `Context` тоже живет в памяти и связан с жизненным циклом клиентов.

Практическое следствие:

- рестарт процесса приводит к потере клиентских сессий;
- reconnect после рестарта закончится `AppReloadMessage`, а не восстановлением старого runtime state.

## Disconnect и grace period

После потери transport BFF не уничтожает клиента мгновенно. По умолчанию действует grace period `15 минут`.

Что это дает:

- временный обрыв WS не всегда ломает сессию;
- мобильный клиент может восстановиться с тем же token;
- пользователь не теряет состояние сразу.

Что это не дает:

- восстановление после рестарта процесса;
- бесконечное хранение сессий;
- горизонтальное шаринг-хранилище между инстансами.

Пока transport отключён, BFF не шлёт сообщения в сокет (`detachTransport`), а для **reliable**-исходящих дополнительно вызывается `ReliableDelivery.pause()`: retry-таймеры останавливаются, pending сохраняется. При успешном reconnect transport прикрепляется заново (`attachTransport`), срабатывает `reconnect$` → `ReliableDelivery.resume()`, и накопленные reliable-сообщения переотправляются. Если grace period истёк — `Client.destroy()` очищает pending. Подробнее — в [`message-delivery.md`](message-delivery.md).

## Что происходит при reconnect

С reconnect полезно мыслить тремя сценариями:

1. Клиент переподключился быстро, token еще жив: BFF отправляет `AppReconnectInfoMessage`.
2. Клиент пришел со старым token, но состояние уже удалено: BFF отправляет `AppReloadMessage`.
3. Сервер перезапущен: предыдущий runtime state потерян, нужна полная переинициализация.

Из этого следует простое правило: UI и бизнес-логика должны быть готовы к полному восстановлению состояния после reload.

Отдельно важно понимать границу transport-слоя: reconnect и reload решают судьбу клиентской сессии в целом, а reliable delivery решает судьбу отдельных сообщений внутри живой сессии. При `destroy()` / `detach` pending-сообщения и retry-таймеры очищаются, поэтому после полной потери runtime state полагаться на незавершённые pending-циклы нельзя. Подробности — в [`message-delivery.md`](message-delivery.md).

## Несколько серверных инстансов

Без дополнительной инфраструктуры matreshka — локальный in-memory runtime. Это значит:

- разные инстансы не делят один и тот же `Client`;
- token сам по себе не гарантирует восстановление на другом процессе;
- балансировка без session affinity может приводить к `AppReloadMessage`.

Если вы ставите matreshka за прокси или балансировщик, полезно заранее решить:

- нужна ли sticky session;
- как долго transport может простаивать;
- допустим ли reload клиента после переключения upstream.

## NGINX, прокси и таймауты

В реальной эксплуатации transport часто рвется не из-за приложения, а из-за промежуточного слоя.

На практике стоит проверить:

- idle timeout для `WS`;
- keep-alive настройки;
- проксирование `SSE`, если используется событийный поток;
- buffering и long-lived connection ограничения.

Если transport нестабилен, matreshka все равно попытается восстановить сессию через reconnect, но лучше уменьшить число лишних reconnect-циклов.

Даже с включённой reliable delivery это остаётся актуальным: повторная отправка отдельных сообщений не заменяет здоровое соединение и не спасает после потери памяти процесса. Она лишь закрывает кратковременные transport-level потери внутри текущей сессии.

## Ресурсы на активного клиента

У каждого активного клиента есть цена:

- объект `Client`;
- подписки на transport;
- зарегистрированные component handlers;
- `Context` и связанные подписки;
- potentially cached/generated components, например у `forEach`.

Поэтому важно:

- не держать тяжелые данные в per-client state без необходимости;
- вовремя удалять временные entry-компоненты;
- **вызывать `Context.destroy()`** для состояния, привязанного к странице/диалогу, когда entry больше не используется (навигация внутри сессии сама контексты не снимает) — см. [context-destroy-scenarios.md](../advanced/context-destroy-scenarios.md) и [context-lifecycle.md](context-lifecycle.md);
- учитывать **`persistent: true`**: такие контексты **переживают** отсутствие клиентов до явного destroy; планировать инвалидацию и не копить process-wide state без необходимости;
- аккуратно работать с большими списками и real-time страницами.

## Ограничения сложности UI

matreshka — это DSL компонентов, а не произвольный low-level DOM API. Отсюда следуют ограничения:

- дизайн ограничен возможностями готовых компонентов;
- сложные кастомные визуальные паттерны могут потребовать расширения клиента и shared-контрактов;
- часть UI-компромиссов надо принимать на уровне DSL, а не CSS-пиксель-перфекционизма.

Если проекту нужен очень свободный и визуально сложный фронтенд, это стоит честно оценить заранее.

## Порог входа

Чтобы эффективно писать на matreshka BFF, обычно нужны:

- уверенный TypeScript;
- понимание OOP-модели компонентов;
- понимание `RxJS`, хотя бы на уровне `Subject`, `BehaviorSubject`, `Subscription`;
- понимание `zod`, если используется валидация `Context`.

Это не критика, а важный фактор оценки команды и сроков входа.

## Ошибки и наблюдаемость

У `Client` есть `error$`, и его полезно подписывать в transport-слое:

```ts
client.error$.subscribe((error) => {
  console.error(error);
});
```

Это простая, но важная практика. Она помогает поймать:

- ошибки в server actions;
- ошибки валидации `Context`;
- ошибки сериализации и dispatch.

## Best practices

### 1. Держите бизнес-логику на BFF

Если можно выбрать между серверным решением и усложнением runtime-клиента, чаще всего лучше серверное решение.

### 2. Разделяйте transport и доменную логику

Transport должен только:

- получить/создать `Client`;
- передать `newMessage(...)`;
- отправить наружу `outcomingMessage$`;
- сообщить о disconnect.

Всю бизнес-логику лучше держать в `Page`, `Context`, component actions и platform handlers.

### 3. Делайте страницы маленькими и композиционными

Лучше:

- несколько небольших контекстов;
- простые page-классы;
- повторно используемые компоненты и helper-ы.

Чем один гигантский `Page` на все случаи жизни.

### 4. Используйте `zod` там, где клиент может менять данные

Хорошая минимальная привычка:

```ts
context = new Context({
  schema: z.strictObject({
    email: z.string().email(),
  }),
  data: async () => ({
    email: "",
  }),
});
```

Это особенно полезно для input-форм, filters и всех сценариев, где данные приходят обратно с клиента.

### 5. Не забывайте про `emitAfterInPlaceMutation()`

Если данные были изменены in-place, а не через `setValue`, клиент обновления не увидит.

Правильно:

```ts
const data = this.context.data$!.getValue();
data.items.push({ id: "1", title: "Новый" });
this.context.emitAfterInPlaceMutation();
```

### 6. Не переусложняйте первые страницы

Для старта достаточно:

- одного `Page`;
- одного `Context`;
- одного `textInput`;
- одного `form`;
- одного `button` с `onSubmit`.

Этот путь быстрее и безопаснее, чем сразу строить сложные многоуровневые экраны.

### 7. Думайте о reload как о нормальном сценарии

Даже если reconnect обычно срабатывает, приложение должно корректно переживать полный reload:

- route должен быть восстановим;
- начальные данные — повторно вычисляемы;
- важные значения не должны жить только в памяти, если их потеря недопустима.

## Когда matreshka особенно хороша

Архитектура особенно сильна, если:

- интерфейс в основном определяется серверными данными;
- нужен быстрый BFF-driven UI;
- есть несколько платформ с близкой логикой;
- клиент должен оставаться максимально универсальным.

## Когда стоит заранее быть осторожнее

Вопросы, которые полезно задать до масштабирования:

- насколько критична потеря in-memory state;
- нужен ли multi-instance deployment;
- насколько сложен целевой UI визуально;
- не станет ли per-client state слишком тяжелым;
- есть ли у команды достаточный опыт с TypeScript, RxJS и message-driven подходом.

## Практический итог

Если нужна короткая выжимка, то она такая:

- matreshka хорошо подходит для BFF-first UI.
- Главная цена архитектуры — in-memory lifecycle и ограничения DSL.
- Самые важные инженерные привычки здесь: маленькие страницы, валидируемые контексты, аккуратный transport и готовность к reconnect/reload.
