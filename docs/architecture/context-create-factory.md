# Зачем нужен `createContext` (а не `new Context`)

Этот документ объясняет, почему в `@matreshka/bff/core/context/context-create.ts` есть отдельная фабрика `createContext`, какие проблемы она решает и почему их нельзя надёжно закрыть только через ООП-конструктор класса `Context`.

Связанные документы:

- жизненный цикл контекста: [`context-lifecycle.md`](context-lifecycle.md);
- практическое использование API: [`../guides/context.md`](../guides/context.md).

## Проблема, которую решает фабрика

`Context` хранит runtime-состояние и умеет валидировать входящие client updates через `schema` (Zod).  
Ключевая архитектурная задача: **на этапе компиляции** гарантировать, что `schema` совместима с `data`.

Под «совместима» здесь понимается:

- в `schema` нет ключей, которых нет в `data`;
- типы полей `schema` (через `z.output`) не конфликтуют с типами `data`;
- допускается подмножество полей и вложенные partial-ветки.

Если не проверять это в compile-time, ошибка проявится уже в runtime (или хуже — часть проверок будет неявно обходиться).

## Почему один только ООП-класс это не закрывает

У конструктора `new Context(...)` есть ограничения TypeScript DX:

- сложные conditional-overload проверки с хорошей диагностикой проще описывать на уровне функции-фабрики;
- при попытке кодировать те же проверки только через конструктор сообщения ошибок становятся хуже и менее предсказуемыми;
- конструктор легко использовать как «сырой runtime-вход», обходя intended compile-time guard.

Иными словами, класс отлично решает **поведение** (lifecycle, sync, destroy), но хуже подходит как точка входа для сложного type-level контракта `schema ↔ data`.

## Архитектурное разделение ответственности

В текущем дизайне роли разделены:

- `Context` — runtime-механика (инициализация, watch/set/replace, доставка diff, lifecycle);
- `createContext` — compile-time контракт и удобный API создания.

Поэтому создание контекста должно идти через фабрику:

- `createContext({ data, schema?, preload?, persistent? })`.

А прямой `new Context(...)` ограничен (`protected constructor`), чтобы не обходить type-level валидацию по ошибке.

## Зачем оставлен внутренний runtime-вход

`Context.createRuntime(...)` существует как **внутренний** мост между фабрикой и классом.

- он нужен для реализации `createContext` после ограничения конструктора;
- помечен как internal/deprecated для пользовательского кода;
- запрещён линтером в прикладных местах, чтобы не использовать его напрямую.

Это компромисс: строгий публичный API + минимально необходимый технический вход для внутренней связки.

## Итог

`createContext` — не «лишняя обёртка», а отдельный архитектурный слой type-safety.  
Он предотвращает класс ошибок в конфигурации `schema`/`data` и даёт более понятные compile-time diagnostics, чем попытка опереться только на `new Context(...)`.
