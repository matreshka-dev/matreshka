# Жизненный цикл Context

Документ описывает, как `Context` живёт на BFF и на клиенте, как связаны протокольные сообщения и почему **уничтожение на сервере** и **удаление локальной копии на клиенте** — разные этапы.

Практика работы с API контекста — в [guides/context.md](../guides/context.md). Формат сообщений — в [protocol.md](protocol.md).

## Роли

| Сторона    | Ответственность                                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **BFF**    | Единственный источник правды: загрузка данных, бизнес-логика, рассылка diff клиентам, **освобождение памяти** при завершении сценария.                                                     |
| **Клиент** | Локальная копия values для UI, реакция на `change$`, обратная отправка правок через `context-values`. Snapshot на клиенте **не обязан** исчезать в тот же момент, что и запись на сервере. |

## Этапы на BFF (общая схема)

1. **Создание** — `new Context({ data, schema, … })`, регистрация id в registry.
2. **Привязка клиента** — `authorizeClient` / сериализация ref в дереве компонентов; при необходимости `init()` и **`context-init`** (полный snapshot).
3. **Работа** — изменения через `setValue` / `data$`, исходящие **`context-values`** (diff) всем привязанным клиентам; входящие **`context-values`** от клиента (с валидацией schema).
4. **Использование entry** — page/dialog держит instances; `stopUsing$` entry часто совпадает с моментом, когда контекст больше не нужен серверу (см. `destroyContextWithEntry` в приложении).
5. **Уничтожение на сервере** — `context.destroy()`:
   - контекст помечается destroyed, **недоступен** для `value()`, `setValue`, новых ref в сериализации;
   - отписываются подписки, завершается `data$`;
   - всем привязанным клиентам уходит **`context-destroy`** (см. ниже);
   - запись снимается с registry (освобождение памяти на BFF).

Повторное обращение к уничтоженному контексту на BFF — ошибка (`Context … has been destroyed`). Это намеренно: id больше не представляет живое состояние.

## Сообщение `context-destroy`: уведомление, а не «удалить UI сейчас»

`context-destroy` — **уведомление клиентам**, что на **сервере** контекста с данным `target` (id) **больше нет**:

- бессмысленно слать **`context-init`** или **`context-values`** на этот id с клиента — BFF не примет их как к живому контексту;
- сервер **не хранит** values и не будет присылать новые diff по этому id.

Это **не** команда «немедленно убрать все компоненты с экрана». Смена страницы, dialog, `AppPageMessage` и teardown дерева UI идут **отдельным потоком** и могут **слегка отставать** от `context-destroy` по времени доставки.

Семантика для клиента:

| Состояние на клиенте                                                  | Смысл                                                                           |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Активный контекст                                                     | Синхронизация с BFF включена (`context-values` в обе стороны).                  |
| **`pendingDestroy`** (после `context-destroy`, пока есть потребители) | Snapshot только для **чтения** UI; исходящие правки на BFF **не отправляются**. |
| Контекст evict из hub                                                 | Локальной копии нет; `value(ref)` для этого id недоступен.                      |

## Жизненный цикл на клиенте (holds)

Клиент учитывает, **какие узлы дерева конфигов** (ComponentHub / `ConfigEntry`) зависят от каждого `contextId`. Для **hold** это объединение: базовый `sourceConfig`, **все** `rules` (conditions и overrides каждого правила, в том числе неактивного), conditions/actions компонента, ref и плейсхолдеры `@{…}` — см. `calculateEntryHoldContextIds`. Runtime-граф `contextDependencies` (ready$, rerender) по-прежнему строится от **resolved** конфига (только активные overrides). Счётчик потребителей и diff по entry — в `ComponentContextDependencyHolds`; `ContextHub` читает `holdCount` при `context-destroy`, evict при последнем `removeConsumer` — через `bindEvictHandler`.

**Общие правила:**

1. При регистрации конфига и при пересчёте resolved hub синхронизирует **hold** по полному набору id из `calculateEntryHoldContextIds` (смена active rules **не** снимает hold с контекстов из неактивных overrides).
2. При `deleteConfig` (снятие узла с `useCount → 0`) — **release** hold.
3. При **`context-destroy`**:
   - если **holdCount === 0** — контекст сразу удаляется из `ContextHub` (как раньше);
   - если **holdCount > 0** — контекст переводится в **`pendingDestroy`**: snapshot остаётся, пока хотя бы один компонент в store ссылается на этот id через граф зависимостей.
4. Когда последний hold снят и контекст уже в `pendingDestroy` — выполняется **evict** (физическое удаление из map).

Так клиент:

- не падает на `value(ref)`, пока старое дерево UI ещё смонтировано;
- **не держит** snapshot дольше необходимого — после ухода всех потребителей память на клиенте освобождается.

`loaded(contextId)` на клиенте **true** и для active, и для `pendingDestroy` (чтобы `ready$` не инициировал лишний `context-init` на уже «мёртвый» на BFF id).

Повторный **`context-init`** с тем же id (новый заход на экран / dialog) создаёт **новый** активный контекст на клиенте; holds пересчитываются при register.

## После удаления контекста на BFF: что считать недоступным

На **сервере** после `destroy()`:

- нельзя читать/писать данные через этот `Context`;
- нельзя сериализовать `Context` / `ContextRef` в исходящее сообщение — `toJSON()` падает с ошибкой.

На **клиенте** после evict:

- `ContextHub.value()` для путей с этим id бросает `ContextNotLoadedError` (или эквивалент «не loaded»).

Между `context-destroy` и evict клиент может **ещё читать** snapshot (`pendingDestroy`) — это осознанный компромисс, а не «контекст снова жив на сервере».

## Антипаттерны (архитектура)

### Сообщения BFF → client с ref уничтоженного контекста

Если в JSON сообщения попадает сериализованный `ContextRef`, а к моменту `JSON.stringify` контекст уже **destroyed**, BFF **не отправит** сообщение (ошибка при сериализации). Transport может только залогировать сбой.

Это **сигнал непродуманного порядка teardown**, а не повод «разрешить» zombie id в протоколе. Правильнее:

- сначала снять/обновить UI (закрыть entry, отправить новую page);
- отложить async, который мутирует контекст после `stopUsing$`;
- не вкладывать живые ref в сообщения, которые могут уйти **после** `destroy()` (eager-сериализация ref в строки при `serialize()`).

### Полагаться на то, что клиент удалит контекст в тот же тик, что и `context-destroy`

На клиенте удаление локальной копии **привязано к потребителям в ComponentHub**, а не к моменту получения `context-destroy`. Код, подписанный на глобальный `change$`, должен фильтровать события по ref / не читать id после evict.

### Долго держать page-scoped контекст без destroy на BFF

Entry-scoped контексты нужно завершать на сервере (`destroy()` или паттерн привязки к `stopUsing$`), иначе растёт память BFF и остаются фоновые подписки. Уведомление `context-destroy` как раз сообщает клиентам, что **синхронизация по этому id прекращена**.
